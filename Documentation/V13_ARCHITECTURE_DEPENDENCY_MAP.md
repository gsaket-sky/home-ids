## Ollama local-model spike (Phase 0, decision #3 — "must also work running locally on the Pi")

Real structured-output accuracy test against Phase 51's actual contract (`ollama_soc.py`'s system prompt + JSON schema), not a toy prompt. Three cases: a clear-benign smart-TV telemetry pattern, a clear-malicious DGA/C2 pattern (real TI/AbuseIPDB/VT hits), and the specific trap case this whole HEE review was originally about — zero threat-intel score but a real `malicious_ja3` fingerprint match, which the system's own `ATTACK_SHAPED_EVIDENCE_TYPES` design says a device-type explanation must never override.

**Round 1 — prose-described schema (`"classification": "benign|malicious"` as inline docs), `"format": "json"`:**

| Model | Size | Latency | Valid JSON | Classification correct (3 cases) | Notable failure |
|---|---|---|---|---|---|
| `qwen2.5:0.5b` | 397MB | ~3–11s | Yes | 0/3 | Echoed the literal `"benign|malicious"` placeholder instead of picking one value; evidence returned as wrong-shaped objects instead of strings; failed the trap case with **empty** supporting evidence, exactly the failure mode `ATTACK_SHAPED_EVIDENCE_TYPES` exists to prevent. |
| `llama3.2:1b` | ~1.3GB | ~5–8s | Yes | 0/3 | Same placeholder-echo bug; missed the clear-malicious DGA/C2 case entirely (confidence 1.0 benign); failed the trap case with `recommended_action: "suppress"` — would have suppressed a real JA3-matched threat. |
| `qwen2.5:3b` | ~1.9GB | ~6–8s | Yes | 0/3 | Same placeholder-echo bug; fabricated evidence not present in the payload ("device sends ads through DNS query patterns" — invented); failed the trap case again with empty supporting evidence. |

**Consistent 0/3 across a 6x size range (0.5B→3B) on the exact same bug (literally copying the `"value1|value2"` prose-schema notation) is suspicious enough to be a prompt-conveyance issue, not a pure reasoning-capability ceiling** — confirmed below.

**Incident (2026-09-05): testing against `.94`'s own live Ollama caused real production contention.** `.94`'s `llama-server` runs with `-np 1` (one request processed at a time). A benchmark test's client-side `urllib` timeout does NOT cancel the request server-side — it keeps processing/queuing regardless of whether the client gave up. Running 16 test requests (8 cases × 2 prompt variants) against this single-slot production instance queued up work that then blocked production's own scheduled `ollama_soc.py` cron run (started 20:30) from getting a response. Caught by checking `ps aux` for `ollama_soc.py` and `curl .../api/ps` for the loaded model state; fixed by killing the interfering test process. Production's job was not crashed by this, just delayed — but this could have gone unnoticed without an explicit check. **Rule for future testing against `.94`'s Ollama**: never send more than one in-flight request at a time, and always verify no test process is still running server-side (not just client-side "done") before considering a test finished. Prefer testing against `.19`'s separate Ollama instance for anything not specifically about production's own model.

**Deferred (user decision, 2026-09-05)**: whether production's actual `llama3.1` model hits the same placeholder-echo bug (`"classification": "benign|malicious"` literal) found in the small local models is still unconfirmed — the test was aborted mid-run to protect production. **Pick this back up in a quiet window**: confirm no `ollama_soc.py` run is active first, send exactly one request at a time, and verify via `ps`/`curl .../api/ps` that the server has actually finished before sending the next — not just that the client call returned. The proposed fix itself (swap `_query_ollama()`'s literal `"format": "json"` for a real JSON-schema object) is considered safe/beneficial regardless of this test's outcome, but stays unapplied until the user decides to act on it — see the plan's discussion of this choice.

**Round 3 — real historical production alerts (`state/alerts.json` on `.94`, 35,019 lines), not synthetic cases** (2026-09-05): built via the actual production prompt-building functions (`_build_evidence_only_payload`/`_evidence_relevance_breakdown`/`_candidate_alternate_hypotheses`, imported directly from `ollama_soc.py` for fidelity), run with the JSON-schema-constrained fix from Round 2.

**Real-data caveat, found empirically**: every `hee_evidence_types`-tagged alert in this dataset has `risk >= 4.0` — that's the tagging threshold itself, so there's no natural "confirmed benign" counterpart at this evidence tier (benign traffic never reaches this stage), and only 21 unique (device, signature) combinations exist among all hee-tagged rows in the whole history — the real ceiling of diversity available, not a sampling shortfall. This run therefore measures **real-world malicious recall + evidence quality on genuine historical attack-shaped alerts** (20 of the 21 unique cases, all reference-labeled malicious), not a balanced accuracy score.

| Model | Real recall | Avg latency | Notable behavior |
|---|---|---|---|
| `qwen2.5:0.5b` | **1/20 (5%)** | 34.8s | Reversed almost completely from the synthetic Round 2 result (3/3 there). Called a `risk=9.5`, `hard_stop`-path Geofencing Policy Violation "benign," hallucinating "DNS covert tunneling" as its own reasoning for that call — the single most severe case in the sample, missed outright. |
| `llama3.2:1b` | 9/20 (45%) | 67.1s | Best real recall of the three — still misses more than half of genuine escalated alerts. |
| `qwen2.5:3b` | 6/15 completed (40%), **5/20 outright timed out** (180s cap) | 139.9s avg on completed calls, up to 176.9s | A quarter of real cases never got an answer at all within a generous timeout — impractical latency for this hardware regardless of accuracy. |

**Resolution (2026-09-05, user decision)**: local mode is scoped down to lightweight triage only (a coarse "does this need deeper review" signal) — full structured Tier-2 analysis stays on a remote, more capable model, matching today's production architecture for the hard cases. This revises decision #3 in the plan. **Not yet validated**: whether small models are actually reliable at the simpler triage task — that's a new, separate spike, not an assumption. Don't treat "triage" as solved just because it sounds easier than the full task did.

**This reverses the takeaway from the synthetic-only spike.** The earlier "smallest model had the best accuracy" conclusion (Round 2, n=3 synthetic) does not hold on real data — synthetic cases were evidently too clean/obvious (extreme entropy/DGA scores) to be representative of the far more common `risk=4.0` borderline `NETWORK_INTRUSION` alerts that dominate real traffic. **No model tested is currently trustworthy for this task**: a 45%-recall local reviewer on a security system means missing more than half of genuinely escalated threats, and the one model fast enough to be practical (0.5B) is also the least reliable on real data (5% recall). This is a genuine, unresolved feasibility question for decision #3 ("Ollama must also work running locally"), not a solved one — see the open strategic question this raises, to be discussed with the user directly rather than assumed away.

**Round 2 — real JSON-schema-constrained decoding** (Ollama's `format` field given an actual JSON Schema object with `"enum": ["benign", "malicious"]`, decoded at the token level, not just described in prose):

| Model | Classification correct (3 cases) | Latency | Notable behavior |
|---|---|---|---|
| `qwen2.5:0.5b` | **3/3** | ~6–11s | Placeholder-echo bug gone entirely. Best accuracy of the three, but `supporting_evidence` is thin/generic (empty on one case) and one hypothesis name was wrong (`LOCAL_DEVICE_DISCOVERY` for what should be `DGA_BOTNET_C2`) even though the binary classification landed correctly. |
| `llama3.2:1b` | 2/3 | ~10–28s (noticeably slower under schema constraint) | False-positive on the clear-benign case (called it malicious). Evidence strings on the malicious case leaked raw prompt-formatting artifacts (`"device[ip]=...`, `"threat_intel_hit\`: False,"`) — messy, landed on the right label without clean grounded reasoning. |
| `qwen2.5:3b` | 2/3 | ~35–47s (markedly slower) | Also false-positive on the clear-benign case — worse than a miss, it **fabricated** a claim not in the payload ("`samsungcloudsolution.com` specifically relates to a known C2 domain," which is untrue). But its reasoning on the two cases it got right was clean and specifically evidence-grounded (cited `dga_score:0.92`, `malicious_ja3` directly).

**Conclusions from this initial spike (n=3 per model — a real signal, not yet a statistically robust one)**:
1. **Actionable regardless of model choice**: v13's Ollama client should always use real JSON-schema-constrained `format`, never a prose-described enum — this eliminated an entire class of failure outright and should be considered a fixed requirement of the design, not a per-model workaround.
2. **The smallest model (0.5B) had the best binary-classification accuracy** in this sample, with the best latency — counter to the naive assumption that bigger is safer. Its weakness is evidence-citation specificity (generic, sometimes empty `supporting_evidence`), which the real `DeterministicValidator` already rejects outright for benign verdicts — so its practical reliability may be better than the raw classification-accuracy number suggests, once wired through the actual validator.
3. **Both larger models produced false positives on the easy benign case** — the safer failure direction for a security system (over-alerting vs. missing a real threat) but still a real cost (alert fatigue), and the 3B model's outright fabrication on that case is a genuine concern for trustworthiness at any size.
4. **Latency scales badly with schema-constrained decoding as model size grows** on this hardware (~8s → ~45s from 0.5B to 3B) — a real consideration for whatever a genuine Raspberry Pi's weaker CPU would do to these numbers.
5. **Not a final model-selection decision** — three synthetic cases is a spike, not a benchmark. Before committing to a specific model for v13's local-Pi mode, this needs a larger evaluation set built from real historical alerts (`state/alerts.json`), not synthetic ones, and should specifically stress-test evidence-citation quality (not just the binary label) against the actual `DeterministicValidator` checks, not just raw JSON validity.

## Triage-task spike (Phase 0, following decision #3's resolution)

Tests the SIMPLER task local Ollama was scoped down to (a coarse `needs_review: bool` flag, not full Tier-2 analysis) — not assumed to work just because it's simpler than the full task that failed. Recall measured on 10 real historical escalated alerts (should all be `True`); specificity measured on 5 constructed routine cases (a smart TV, printer, smart plug, laptop OS-update check, smart speaker — all clearly synthetic, since this dataset has no natural routine counterpart at the hee-tagged tier, same limitation noted in Round 3). Run against `.19`'s Ollama, one request at a time, per the incident lesson above.

| Model | Recall on real threats | Specificity on routine cases | Avg latency |
|---|---|---|---|
| `qwen2.5:0.5b` | 8/10 (80%) | **0/5 (0%)** | 18.2s |
| `llama3.2:1b` | **10/10 (100%)** | **0/5 (0%)** | 30.6s |
| `qwen2.5:3b` | 8/8 completed (100%, 2 timeouts) | 1/5 (20%) | 71.6s |

**Recall is genuinely solved** — a dramatic improvement over the full-task benchmark (5–45% there), confirming the triage-only architectural decision is directionally sound: none of these models silently drops a real threat when only asked the simpler question.

**Specificity is not solved, and this matters**: every model flags almost everything as `needs_review: true`, including the most mundane cases (a printer's firmware check, a smart plug's routine cloud check-in). The system prompt's explicit "bias strongly toward flagging ANY hint of irregularity" instruction, combined with small models' general caution, means the triage step currently provides **zero actual filtering value** — it would forward essentially everything to full remote review anyway, which defeats the purpose of having a lightweight local pre-filter (though it's at least safe, never silently dropping something real, unlike the full-task result). **Deferred by explicit user decision (2026-09-05), not blocking**: prompt/calibration work to reduce false-positive triage flags without sacrificing the recall just achieved is real, unattempted work — but "safe, not yet efficient" is an acceptable interim state (a triage step that forwards everything is no worse than not having one, since it never silently drops a real threat). Revisit when convenient; does not block Phase 1 or the rest of Phase 0.

### A14. Full-architecture plan, Phase 1: `GraphStore` becomes `.94`'s real live audit trail + windowed reads (2026-09-06)

**Why**: A13's fast cutover swapped the decision/hypothesis *computation* to v13's engine, but deliberately left `GraphStore` completely out of `.94`'s live loop — the decision engine only ever saw one cycle's fresh evidence, same as v-current's `EvidenceStore` always did. This phase is the user's explicit follow-up: cover the full remaining architecture (see the approved plan file), starting with the graph itself, since identity resolution/CL-AFPE v13/retro-hunter v13 all depend on `.94` having a real, populated graph — right now only `.19`'s separate comparison daemon does.

**A real bug found and fixed, not assumed**: `src/v13/graph/store.py`'s `prune_evidence()` has always had a "don't delete evidence a decision still references" exception — but nothing ever created the `evidence→decision` edge that exception's query looks for (`insert_decision()` never called `add_edge()`). It was silently dead code; pruning would have deleted evidence a decision's `raw_payload_json` still pointed to. Fixed: `insert_decision()` gained an `evidence_ids` param that creates a real `supports` edge per item; `src/v13/ingest/sources.py`'s `compute_decision()` (the only other real caller) updated to pass it. New tests in `tests/test_v13_graph_store.py` prove referenced evidence survives pruning while unreferenced evidence is still pruned normally (a regression guard against the fix accidentally making everything immortal).

**Write-cost fix, benchmarked before wiring in, not after** (per the plan's own explicit instruction): `GraphStore` gained `transaction()` (a context manager) and `_maybe_commit()` (every mutating method now calls this instead of `self._conn.commit()` directly) — outside a `transaction()` block, behavior is byte-for-byte unchanged; inside one, every write in the block shares a single commit. A throwaway benchmark (not committed — matches the plan's own "not new production code" instruction) simulating `.94`'s real 48-device count at its real 2s poll cadence measured **worst-case per-cycle write latency dropping from 360ms (18% of budget) unbatched to 22ms (1.1% of budget) batched** — a ~16x improvement, real headroom for burst scenarios a synthetic 6-active-devices/cycle load doesn't fully capture.

**Windowed reads wired into `src/v13/ops/live_engine.py`, with a design correction found while implementing it**: the plan's original framing ("query a longer window to catch cross-cycle patterns") turned out to be subtly wrong — confirmed by reading `src/v13/hypotheses/engine.py`'s `compute_freshness()` directly, which already caps usable evidence at 600s (default) / 86400s (reputation family), identical to v-current's own `EvidenceStore` TTLs, regardless of how much history a caller queries. A wider window than that returns nothing scoring wouldn't already discard. The REAL, honest value-add is **restart survival**: `EvidenceStore` is 100% in-memory, wiped on every `soc.service` restart; the graph isn't. `evaluate()` now queries `RollingWindowView.evidence_in_window(device_id, window_seconds=86400)` (the longest TTL that matters — `compute_freshness()` does the real per-item trimming after) and merges it with the current cycle's fresh evidence before deciding, then writes the fresh evidence + resulting decision back via one `store.transaction()` call. Both directions are best-effort (a graph failure degrades to fresh-evidence-only / skips the durable write, never raises into the caller or blocks a real decision) and `device_id=None` (unpassed) skips all of it, unchanged from A13's original behavior — existing callers that never adopted this stay exactly as they were.

**A read-latency benchmark too**, since the read is now also in the hot path: a deliberately pessimistic 2,880-row/day single-device history (one item every 30s continuously) queried at the full 86400s window in 36-62ms worst case — comfortably within budget alongside the write side.

**A deliberate, documented exclusion**: the geofencing block's second, separate `decision_engine.evaluate()` re-evaluation (after appending fresh `geofencing_violation` evidence) does NOT get `device_id`/`now` passed — `v13/evidence/ingest.py`'s `convert()` assigns a fresh `evidence_id` on every call with no content-based dedup, so re-converting the same `active_evidence` list a second time in the same cycle would silently double-insert every item as genuine duplicate graph rows. This second call site stays graph-uninvolved until that's worth solving properly (same "known limitation, not a new gap" framing A13 already used for this exact call site).

**Verified**: `tests/test_v13_graph_store.py` (+9 checks: the pruning-exception fix, `transaction()`'s atomicity/batching/nesting behavior). `tests/test_v13_live_engine.py` (+12 checks, Section E): a two-cycle scenario where cycle 1's `zeek_lateral_scan` evidence alone stays SUSPICIOUS, cycle 2's OWN fresh evidence (`malicious_ja3`) would also alone stay SUSPICIOUS, but cycle 2 actually reaches HIGH because the graph read pulled cycle 1's still-fresh evidence back in — the concrete "behavioral pattern across cycles" proof the plan called for. All 18 `tests/test_v13_*.py` files and v-current's golden-case regression suite (`test_phase38`/`34`/`54`/`42`) re-confirmed clean.

**Deployment status (final, 2026-09-06)**: deployed and restarted on `.94`. Two real bugs were found live within the FIRST FEW MINUTES of running with A14's graph writes active, both fixed and deployed as immediate follow-up commits before this entry was written:

1. **Decision-row explosion** (commit after A14): `live_engine.py` never had the equivalent of `src/v13/ingest/daemon.py`'s own `_last_decision_key`/`only_persist_if_changed_from` dedup — confirmed live: 611 decisions-table rows in well under a minute, one new row per device on EVERY 2s cycle regardless of whether the verdict changed. **New: `src/v13/ops/live_prune.py`** — the real gap the whole incident exposed: nothing on `.94` was enforcing `GraphStore`'s own documented 90-day evidence retention at all (`.19`'s daemon prunes on its own internal schedule; `.94`'s new write path never got the equivalent). 2. Persists each anchor's learned MAC via `GraphStore.update_device_metadata()`/`get_device_metadata()` (two new `GraphStore` methods, shallow-merge semantics) instead of v-current's own single in-memory `_gateway_mac` field — survives a `soc.service` restart instead of relearning it from scratch.
3. **A third real bug — this one active in production, found by the closer-than-usual post-restart monitoring this phase called for**: within 90 seconds of `LiveIdentityManager` first going live, `.94`'s device count jumped 51 → 55 (confirmed via `state/ids_state.json`). The dead branch-6 IP-anchor override (swapping to `stable_device_id(ip)` whenever the raw-MAC-fallback branch fired for a randomized MAC) was removed entirely — it never helped and was itself part of the problem. `tests/test_v13_live_identity.py` Section E was rewritten to lock in the corrected scope, including a direct regression guard reproducing the exact production incident (a locally-administered-looking MAC with an existing persisted binding must keep resolving to that same device_id on a new IP).

**A residual data-integrity note, not a design flaw**: because `core/state_guard.py`'s `_mac_to_device_id` index is *derived* — rebuilt from every `DeviceState`'s own `mac_address` field on load, last-one-wins for any MAC appearing on more than one entry (`state_guard.py:731-739`) — the ~10-minute exposure window left a handful of MACs bound to more than one `device_id` in `state/ids_state.json` (peaked at 6 affected MACs; already down to 5 within the next few minutes as `DeviceIdentityManager`'s own inherited, unmodified `_merge_orphan_if_fragmented()` self-healed one of them automatically). None of the duplicate shadow entries this created carry any alert/threat history (`confirmed_threat_count`/`last_alert_time` both zero on every one checked) — no real security history was lost, only a temporary split of which `device_id` new observations land under for a small number of already-fragmented devices. Deliberately NOT hand-edited under time pressure as a third same-session production-state surgery; left for the existing self-healing mechanism to continue converging, with a note here to spot-check convergence in a follow-up session (`grep`/small script over `state/ids_state.json` for any `mac_address` value appearing on more than one device entry) rather than assuming it resolved silently.

**Deployment status**: code committed, pushed, deployed, and `soc.service` restarted TWICE on `.94` — once to activate Phase 3, once more (after this incident was found, fixed, tested, and re-deployed) to apply the `mac_bindings` correction. ### A19. Full-architecture plan, Phase 1a: cross-device correlation, reputation propagation, genuine first-contact scoring (2026-09-07)

**Why this needed real design, not just wiring**: confirmed via direct grep before starting (not assumed from the plan's own description) that none of Phase 1a's three capabilities existed — `domain_seen_before()` had zero callers, `destinations.reputation_tier_cache` was written by nothing, and no `CoordinatedTargetingHypothesis`/cross-device query existed anywhere. The real design question was architectural: `HypothesisEngine.evaluate_all()`'s signature is `(evidence_list, rep_vector, device_type, baseline_familiarity, now)` — no `store`/`device_id` parameter at all, and its own module docstring calls "every `Hypothesis.evaluate()` takes a fresh per-cycle snapshot" a property `HEE_ROADMAP.md` said not to break. Changing that signature to thread a graph handle through every hypothesis would touch the one invariant this whole rewrite exists to preserve, for hypotheses that don't even care about the new capabilities.

**The design chosen**: all three capabilities are computed in `live_engine.py` (the one place that already has a `device_id` and a graph handle) and injected as ordinary synthetic `Evidence` items into `merged_v2` — the SAME list every hypothesis already reads, via the SAME mechanism the windowed graph-read already uses. No hypothesis signature changed; `HypothesisEngine`/`DecisionEngine` needed zero awareness that some evidence is graph-derived rather than sensor-derived. This keeps the pure-per-cycle-snapshot property fully intact and reuses 100% of the existing scoring machinery (freshness/TTL, independence-family corroboration counting, the Gap-64 domain-linkage filter) for free.

**CRITICAL, and the one thing that could have silently reintroduced Phase 1's own worst bug**: the synthetic items are added ONLY to `merged_v2` (this cycle's scoring input), never to `fresh_v2` (the graph-write path). A synthetic item is re-created fresh every single cycle with `timestamp=ts` — if it ever reached `fresh_v2`, `_content_key()` would see a "new" item every cycle (since its own timestamp always changes) and write a duplicate row forever, recreating the exact 43,342-row evidence-duplication incident Phase 1 found and fixed. Caught during design, not after deploying — `_inject_graph_derived_evidence()`'s own docstring calls this out explicitly, and a dedicated test (`test_v13_live_engine.py` Section F) asserts each synthetic evidence type never appears in `store.get_evidence_for_device()` after a real `evaluate()` call. A second, related fix: `_write_graph()`'s `insert_decision(evidence_ids=...)` call used to pass every id in `merged_v2` — now filtered to exclude anything with the `"v13_live_engine:"` provenance prefix, since an evidence→decision edge pointing at an evidence_id that was never actually inserted would be a dangling reference.

**1. Cross-device correlation** (`COORDINATED_TARGETING`, new hypothesis in `hypotheses/engine.py`): `GraphStore.get_devices_targeting(destination_id, since)` (canonicalizes merged/orphan device_ids so a fragmented device is never miscounted as two independent devices) + `RollingWindowView.devices_targeting()` wrapper. When 1+ OTHER device touched the same destination within `SHORT_WINDOW_SECONDS` (300s), a `coordinated_targeting` evidence item is injected carrying the total device count as `.value`; the new hypothesis scores SUSPICIOUS on 2 total devices, HIGH on 3+ with a confident signal. New independence family `cross_device_correlation` (counts toward corroboration — "another device independently doing this" is a genuinely separate vantage point from any sensor on THIS device).

**2. Network-wide reputation propagation**: new `GraphStore.set_destination_reputation()`/`get_destination_reputation()` (writes/reads the schema's own long-unused `reputation_tier_cache`/`reputation_cached_at` columns). Read side: `live_engine.py` checks the cache for every destination the current cycle's fresh evidence targets, and injects an ordinary `reputation`-family evidence item (reusing the existing evidence_type already read by `ExfiltrationHypothesis`/`BeaconingHypothesis` — no new hypothesis needed) when the cached tier is `>= 5` (ReputationVector's own "corroborated... can justify auto-block" tier) and no older than `_REPUTATION_PROPAGATION_TTL_SECONDS` (86400s, matching `compute_freshness()`'s own reputation-family TTL for consistency — a propagated verdict ages out on the same schedule a directly-observed one would).

**3. Genuine first-contact scoring**: `domain_seen_before()` (already existed, Phase 1) is now actually called — `live_engine.py` checks it for every destination the current cycle touches, with `lookback_seconds` matching `GraphStore.DEFAULT_EVIDENCE_RETENTION_DAYS` (90 days — "seen before" can only honestly mean "within what the graph still retains") and `exclude_window_seconds=SHORT_WINDOW_SECONDS` (so a device's OWN evidence from the current incident doesn't count as "prior familiarity"). When genuinely novel, a `first_contact` evidence item is injected. Wired into `ExfiltrationHypothesis`/`BeaconingHypothesis`/`DNSTunnelingV2Hypothesis` (the "DNS/exfiltration/beaconing" hypotheses the plan named) as an additional `strong_score` contributor. New independence family `novelty_context`, deliberately added to `NON_ATTACK_FAMILIES` (same treatment as `local_device_discovery`) — a novelty fact shouldn't inflate independent-source counts on its own, only inform the specific hypotheses that read it.

**A real pre-existing bug found and fixed as a side effect, not a new decision**: `ExfiltrationHypothesis.evaluate()` computed `strong_score` (from `zeek_beaconing`/`reputation` co-occurrence) but its score-band logic never actually consulted it — only `best` (effective_weight) and `contradicting_score` gated the SUSPICIOUS/HIGH thresholds, making `strong_score` dead weight visible only in the checklist. Found while wiring in the `first_contact` bump (which would otherwise have been equally inert for this one hypothesis, while functioning correctly for `BeaconingHypothesis`/`DNSTunnelingV2Hypothesis`, which already gate on `strong_score`). Fixed additively: `if self.strong_score > 0 and self.contradicting_score == 0: score = max(score, 3.0)` — a new way to reach SUSPICIOUS, never a way to lose an existing high-`best` verdict; confirmed via a regression-guard test that the same weak hit without the corroborating signal still stays at the base floor.

Confirmed live before writing any code: `onnxruntime`, `fastembed`, `sklearn`, and `skl2onnx` are all real installed dependencies in this environment.

**What was ported**, from a direct read of `fp_engine.py`'s real `_stage2_lgbm()`/`_parse_onnx_prob()`/`_stage3_embed()`/`_stage3_rule_fallback()`/`_load_lgbm_model()`/`_load_embed_model()` (lines 1279-1498, 2515-2726): the exact 11-dimension feature vector (`build_feature_vector()` — tranco rank, label entropy, label length, outbound-bytes z-score, device-type bucket, trust-cache hit, lateral-move count, port-scan count, app-protocol weight, arp-sweep count, DNS-evasion ratio, each with v1's own real normalization math), `parse_onnx_prob()`'s dual-format output parsing (skl2onnx ZipMap vs. raw numpy array), the static rule-based Stage 3 fallback, and `combine_scores()`'s exact 3-way weighted-combination logic (`embed is None` → LightGBM alone; `lgbm==0.50` sentinel with embed clearing its own threshold → embed alone; else the real `0.45/0.55` weighted blend).

**Vendor patterns reused, not duplicated**: Stage 3's ~80-line, 52-entry vendor-telemetry pattern list (`_build_safe_vendor_patterns()`) is called directly as an **unbound method** — `AutonomousFPEngine._build_safe_vendor_patterns(None)` — confirmed by reading the method body that it never touches `self` at all, just returns a static list. This avoids copying data that would silently drift from v1's own maintained list, and — the real reason this matters — avoids ever constructing a real `AutonomousFPEngine` instance just to read a static list, since its `__init__` unconditionally starts 3 background daemon threads (the LightGBM/FastEmbed loaders and the weekly-retrain loop) that v13 code must never trigger as a side effect.

**Deliberately NOT ported**: placeholder-model generation (`_generate_placeholder_lgbm`). If v-current hasn't produced a real ONNX file yet, `MLScorer` degrades to Stage 2 unavailable (`None`) — the same "model not ready" fallback v1 itself uses while its own loader thread is still warming up. Generating a second, separate placeholder here would undermine the single-source-of-truth design this whole phase exists to establish.

**Verified**: `tests/test_v13_cl_afpe_ml_scoring.py` (34 checks, requires the venv python for `onnxruntime`/`sklearn`/`skl2onnx`/`numpy`) — every pure function thoroughly (`build_feature_vector`'s all 11 dimensions including negative-value clamping, `parse_onnx_prob`'s both real output shapes, `stage3_rule_fallback`'s real telemetry/CDN checks, `combine_scores`'s all real branches including the exact 0.45/0.55 weighting). `MLScorer.score_stage2()` is tested against a **real** tiny ONNX model generated the same way v1's own placeholder generator does (sklearn `GradientBoostingClassifier` → `skl2onnx`) — genuine `onnxruntime` inference, not a mock, including a discrimination check (threat-shaped input scores materially lower than benign-shaped input, proving the model is actually being consulted). `MLScorer.score_stage3()` is tested against a mocked `fastembed.TextEmbedding` (avoiding a slow, network-dependent ~85MB download during tests, matching this project's own established convention for heavy/network dependencies) while still exercising real cosine-similarity numpy math and the real, non-empty vendor-pattern list reused from v1. Full v13 suite re-confirmed clean.

**Deployment status**: not yet deployed — `MLScorer`/`ClAfpeEngine` remain completely dormant (nothing calls either outside tests), so this commit carries zero live risk, same as Phase 6a/6b/6c.

### A24. Full-architecture plan, Phase 6e: CL-AFPE composed `evaluate()` + shadow-mode wiring (2026-09-07)

**The architectural question this phase had to resolve before writing any code**: the plan said "wire `ClAfpeEngine` into `live_engine.py` in shadow mode," but a direct read of `core/pipeline.py` found v-current's real `fp_verdict = self.fp_engine.evaluate(...)` call (~line 1812) is a SEPARATE, LATER point in the per-cycle flow than where `v13_live_engine.evaluate()` computes the `decision` itself (~line 1298) — the two are not the same call site. Resolved by adding ONE new line to `pipeline.py` immediately after the real `fp_engine.evaluate()` call, calling a new `v13_live_engine.evaluate_cl_afpe_shadow(...)` — mirroring the exact "one new call site, one-line change" shape this module's own docstring already uses to describe the original v13 decision-path cutover, with 100% of the real logic living in `live_engine.py`/`cl_afpe/engine.py`, matching the plan's own wording as closely as is architecturally honest.

**Two more scope decisions, found necessary by reading `fp_engine.py`'s real `evaluate()`/`_stage1_hard_stop()` in full (line 397, line 1088) rather than assumed from this module's own earlier docstrings**: (1) Check 0 (v-current's own decision-engine hard-stop) is reused as v13's own already-computed `decision["state"] == "CRITICAL"` — the same cross-engine-recognition role v1's Check 0 plays for `decision_engine.py`. (2) Checks 1-6 (ThreatIntel IOC, lateral movement, malicious JA3/JA4, honeypot, AbuseIPDB, exfiltration burst) are each RE-PORTED reading `features` directly, NOT approximated from v13's own decision state — confirmed via `decision/engine.py`'s `DEFAULT_HARD_STOP_REGISTRY` that v13's own hard-stop registry only covers honeypot/arp_spoof/geofence/confirmed_exploit; the other six checks feed v13's probabilistic attack-hypothesis SCORE instead, so treating decision state alone as a proxy would silently under-detect exactly the alerts a genuine shadow comparison most needs to catch. Check 7 (local confirmed-intel) is not re-ported a second time — it reuses `check_local_intel_hard_stop()` (Phase 6b) directly.

**A third decision, about state mutation during shadow evaluation**: the composed `ClAfpeEngine.evaluate()` DOES call the real `mark_false_positive()`/`_apply_sigma_shift()`/`record_confirmed_threat()` write paths on a suppress/confirmed-threat verdict, rather than silently no-op-ing them. "Compute-only, never suppresses" (the plan's own verification section) means CL-AFPE's verdict never drives `pipeline.py`'s actual routing — not that shadow mode must be a frozen no-op. These writes only ever touch v13's OWN graph state (`trusts` edges, a device's `fp_profile`/`sigma_shift`) and a v13-ONLY `LocalConfirmedIntel` store (`state/v13_cl_afpe/`, deliberately never `intelligence/local_intel.py`'s real `state/local_confirmed_intel.json` — sharing that file would let a shadow-only ML verdict actually hard-stop v1's own real Stage-1 Check 7 on a later alert, a real live-behavior side effect through a shared file). `MLScorer` is the one deliberate exception to "v13-only": it reads v-current's REAL `models/fp_classifier.onnx`/`fastembed_cache` read-only, matching Phase 6d's own reuse-not-retrain design. Calibration (`_apply_calibration`) is not ported — v1's own docstring already calls it "purely additive to the audit trail, never used for branching," so `calibrated_confidence` is always `None` in the dict this returns.

**A real bug found and fixed while writing this phase's own tests**: `mark_false_positive()`'s default domain/IP immunization branch (written in Phase 6a) had been immunizing the RAW `queried_domain`, not its eTLD+1 base — but `evaluate()`'s own trust-cache lookup (both v1's real one and this phase's newly-composed v13 one) always checks against the BASE domain. A raw-domain immunization would only ever re-match itself, never a sibling subdomain of the same vendor, silently defeating the entire "immunizing sentry.io suppresses xyz.ingest.us.sentry.io too" point of the mechanism — and would have made Phase 6e's own trust-cache-fast-path tests fail outright, which is how this was caught. Fixed to extract the base domain via `utils.etld1()` first (falling back to the raw destination IP when no domain is extractable, matching v1's own real fallback), matching `fp_engine.py`'s real behavior exactly. Two pre-existing tests (`tests/test_v13_cl_afpe.py`'s own "domain vs IP routing" check, `tests/test_v13_integration.py`'s Step 7) had been asserting the old, buggy raw-domain behavior and needed updating to either check the base domain explicitly or use a domain that is its own eTLD+1 base — not a compensating change, a correction to match the fix.

**Verified**: `tests/test_v13_cl_afpe.py` grew from 63 to 79 checks — every Stage 1 check individually (0 through 6, including the real distinct-target gate for lateral movement and the telemetry/CDN exemption for the exfiltration-burst check), the trust-cache fast path (a hit suppresses immediately; a hit still re-runs Stage 1 and overrides on a genuine hard-stop, tuning sensitivity up as a side effect — the non-negotiable Phase-3 fix from v1's own history); both reachable Stage 2/3 final-verdict branches under the deterministic rule fallback (`ml_scorer=None`, matching v1's own "model not ready" behavior); `get_device_suppress_threshold()` actually changing which branch a given combined score falls into; the CONNECTION_ABUSE mutual-exclusivity guarantee proven reachable through the composed `evaluate()`, not just `mark_false_positive()` in isolation; and Check 7's cross-device propagation proven reachable end-to-end through `evaluate()`. A new `tests/test_v13_live_cl_afpe_shadow.py` (12 checks) covers `evaluate_cl_afpe_shadow()` itself: a real end-to-end shadow verdict gets appended to `state/cl_afpe_divergence_v13.jsonl` with a correct `agree`/`disagree` flag against the v1 verdict passed through; a raising CL-AFPE engine never propagates out (pipeline.py's real alert publish must never be affected by a shadow failure) and never appends a fabricated log record; and the shadow local-intel store is confirmed, by path (not just docstring claim), to be separate from v1's real one. Full v13 suite (26 files) re-confirmed clean, including the two pre-existing tests updated for the base-domain bugfix above.

**Deployment status**: this is the first CL-AFPE-related phase this session that is NOT zero-live-risk — `pipeline.py` itself now has one new call site (`v13_live_engine.evaluate_cl_afpe_shadow(...)`, immediately after the real `fp_engine.evaluate()` call) that executes every cycle an alert is being considered. The call is best-effort (wrapped in its own try/except inside `live_engine.py`, never raises out) and compute-only (its return value is discarded by `pipeline.py` — nothing reads it), but it IS new code running in the live per-cycle path on every real alert, unlike Phase 6a-6d's fully-dormant additions. Per the plan's own verification section, this gets the same explain-then-confirm treatment before any `soc.service` restart as every prior live-path change — not deployed to `.94`'s running process as part of this commit; code is pushed/synced, restart requires explicit confirmation.
